# springdoc-openapi

A Spring Boot Orders controller in `OrdersApp.java` whose OpenAPI document and Swagger UI are generated by springdoc, checked by `OpenApiTest`.

## Goal

Show that an OpenAPI 3 spec can be derived from annotated code and Bean Validation constraints, with tests that keep it from drifting.

## Run it

```bash
mvn -q test
```

Expected: `OpenApiTest` runs 3 tests with no failures and Maven reports `BUILD SUCCESS` (verified here: `Tests run: 3, Failures: 0`). To browse it, run `mvn spring-boot:run` and open `/swagger-ui/index.html`; that manual step was not run here, only the MockMvc test of the same page.

## What it proves

- `GET /v3/api-docs` returns a spec titled "Orders API" with the summaries "Place an order" and "Fetch an order by id" taken from `@Operation`.
- Bean Validation shows up in the schema: `@NotBlank` on `sku` makes it required and `@Min(1)` on `quantity` becomes `minimum: 1`.
- `@Schema(example = "ABC-1234")` appears as the example for `sku`, and `/swagger-ui/index.html` answers with status 200.

## Trade-offs

- The spec reflects what the code says; descriptions and examples still need to be written by hand in annotations.
- Annotations in the controller and records add noise to the code.
- Pins: Spring Boot 3.3.5 and springdoc-openapi-starter-webmvc-ui 2.6.0.

## When not to use it

- When you need documentation with narrative, verified examples; `spring-rest-docs` fits better.
- When the contract is designed first and code is generated from it, a spec-first workflow is the better direction.
